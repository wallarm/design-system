# Claude Design

## Set up from a prompt

Paste this prompt into a new Claude Design chat. Claude installs the system for you; nothing
to download or configure.

```text
Install Wallarm Design System in Claude Design.

1. Run this command in your sandbox:
   npx -y @wallarm-org/claude-design@latest export
2. Read wallarm-design-system/SETUP.md and follow every step in it, in order. It publishes
   the system, installs it on a canvas and checks it with a sampler artboard.
3. When the sampler and the app skeleton pass their checks, tell me the system is ready and
   give me its link. Then wait for my design request.

If the command fails or writes no wallarm-design-system/SETUP.md, show me its output and
stop. Don't build the system by hand.

My product: <name>. Menu: <item>, <item>, …
```

The last line is optional. With it, Claude sets up the app skeleton for your product: the
console header and rail, your product's menu and an empty page to design in. Name groups and
section headers in the menu too, for example: `My product: API Security. Menu: Overview, API
Discovery, API Specifications, Sessions; group Detect & Respond: Attacks, Incidents`. Without
it, the skeleton shows a sample product you can rename later.

What you will see:

1. Claude runs the command, which writes `wallarm-design-system/` with the system files and a
   `SETUP.md` written for that release.
2. A new **Wallarm Design System** artifact in your account, with the icon and logo galleries.
   Claude uploads the SVGs in batches of 25 (about 24 calls), then publishes the index. Claude
   gives you its link, `https://claude.ai/artifact/<id>`. **Save it**: you need it to install the
   system on other canvases and to update it.
3. A Design canvas with the system installed and two boards: **Wallarm sampler**, a Users
   settings screen with the app shell, a table, status tabs and an open drawer; and **Wallarm
   app**, your app skeleton. Claude checks that both render without `[WallarmDS]` warnings,
   then waits for your request. Ask for screens and Claude designs them inside the skeleton's
   page. An update never replaces the skeleton: it is your work.

On a canvas, icons come with the components (`WallarmDS.Icons.*`); the galleries are for
browsing them on the system's page. The package `@wallarm-org/claude-design` is published with every stable release and
its version matches the design-system version.

### Update to a new release

Paste this into a chat, with your system's link in place of `<link>`:

```text
Run `npx -y @wallarm-org/claude-design@latest update` and follow wallarm-design-system/UPDATE.md to update my Wallarm Design System: <link>
```

Replace `<link>` with your system's link. It starts with `https://claude.ai/artifact/` and Claude
gave it to you when the install finished. Lost it? Open claude.ai, go to your artifacts, open
**Wallarm Design System** and copy the address from the browser bar. Use your own copy, not
Wallarm's shared system below: Claude can't update that one and will tell you so.

Claude publishes the new files to the same link, uploads only the new and changed icons, asks you
before removing the files the release dropped, and reinstalls the system on your canvases.

## Use Wallarm's shared system

Wallarm's own copy is the
[system artifact](https://claude.ai/artifact/FXWSxmN7zfnpsyMemE5VD7): choose **Wallarm Design
System** when creating a Design canvas. It contains the components, light and dark tokens,
Geist fonts, icons and live examples generated from this repository, and maintainers sync it
by hand (see [Request a change](#request-a-change)).

Choosing the system on a new canvas is enough: Claude starts from the system's README, which
has it put the app skeleton on the canvas first and design every screen inside it. Name your
product and menu in the prompt to set up the skeleton, or ask for a standalone component to
skip it.

Start a prompt with the screen's purpose, content and states: “Use Wallarm Design System to
prototype a rules list with a primary Create rule action, environment filter, empty state and
dark theme.” Ask for the existing components and semantic tokens, then check the component
guides for the intended composition.

## Mount components

Canvas markup uses `x-import`. The namespace is `WallarmDS`; component names are flat, such
as `WallarmDS.DialogContent`. Wrap each artboard in `WallarmDS.Root` so themes and overlays
stay inside it.

```html
<x-import component-from-global-scope="WallarmDS.Root" theme="light">
  <x-import component-from-global-scope="WallarmDS.Button"
    variant="primary" loading="{{loading}}">Create rule</x-import>
</x-import>
```

```js
class Component extends DCLogic {
  renderVals() {
    return { loading: false };
  }
}
```

Use kebab-case for canvas props: `default-open`, `on-value-change`, `class-name`. Strings
can be attributes directly. Pass booleans, numbers, collections, data and callbacks through
holes from `renderVals()`: `loading="false"` is a string, not the boolean `false`. The
artboard has one `class Component extends DCLogic`; state lives in `this.state` and changes
with `this.setState`. Its code is classic JavaScript, without JSX, TypeScript or module
imports.

The canvas supplies React 18. Outside the canvas, the artifact loads `tokens.css`, then
`components/bundle.css`, then `components/bundle.js` after the page's React and ReactDOM.
The npm package continues to use React 19.

## Dark artboards and overlays

Set `theme="dark"` on `WallarmDS.Root` to switch the artboard's semantic tokens. Use the same
Root for Dialog, DropdownMenu, Select and other overlay compositions so their portal content
inherits the theme. Follow each component's guide for its required parts.

For an overlay shown in a static design, return `shown: true` from `renderVals()` and pass
it to the prop the component has: `default-open="{{shown}}"` on DropdownMenu, Select,
Tooltip, Calendar and FilterDropdown; `open="{{shown}}"` on Dialog, Drawer, Popover and
SearchModal, which have no `default-open`. Controlled `open` values need an `on-open-change`
callback if the prototype should also close. Root scopes the theme; ThemeProvider changes
the whole page and should not be used as the canvas wrapper.

The canvas CSS is precompiled: only the classes in `components/UTILITIES.md` exist, and every
numeric utility means N px (`p-16` is 16px). The project README has the Tailwind-to-ours
translation, and Root warns in the console about classes that have no CSS.

The bundle also exposes components available through npm component subpaths, such as the
Dialog family. Root is a canvas-only helper; the package's npm exports stay unchanged.

Icons live under `WallarmDS.Icons`, for example:

```html
<x-import component-from-global-scope="WallarmDS.Icons.Search"
  class-name="icon-md text-icon-primary" aria-hidden="true"></x-import>
```

## From a story to an artboard

Each component guide carries its Storybook stories verbatim — description, source and the
local mocks they import — as reference. The agent reads a story and writes its own artboard
with `x-import` and `DCLogic`, following the translation rule in the system's README: imports
become `WallarmDS.X`, JSX elements become `x-import`, React state becomes `this.state`, and
mock data becomes constants in the script. Props that take a render function, such as a Table
column's `cell`, are built in `renderVals()` with `React.createElement`:

```html
<x-import component-from-global-scope="WallarmDS.Root" theme="light">
  <x-import component-from-global-scope="WallarmDS.Table"
    data="{{rows}}" columns="{{columns}}" get-row-id="{{getRowId}}"></x-import>
</x-import>
```

```js
class Component extends DCLogic {
  renderVals() {
    var h = React.createElement;
    return {
      rows: [{ id: 'event-1', method: 'GET', ip: '192.0.2.10' }],
      columns: [
        { accessorKey: 'method', header: 'Method' },
        {
          accessorKey: 'ip',
          header: 'Source IP',
          cell: function (ctx) {
            return h(WallarmDS.Text, { size: 'xs' }, ctx.row.original.ip);
          },
        },
      ],
      getRowId: function (row) { return row.id; },
    };
  }
}
```

Hooks cannot run in `renderVals()`; the README names the non-hook path for each case, such as
`WallarmDS.toaster.create(...)` from a `DCLogic` handler instead of `useToast`. When a
component's guide has no story for what you need, request the story in the repository.

## Request a change

Change the component, story or token in **wallarm/design-system**, then run
`/claude-design-sync` there after the release. Describe the component, expected behavior,
theme and relevant state when requesting a change; include the canvas or a screenshot that
shows it. The repository is the source of truth, and the artifact is generated from it.

Maintainers sync with the `claude-design-sync` skill: it fetches the export built from the
release tag, plans the exact changes against the artifact, uploads changed assets, publishes
the changed files with the index last, and checks that the artifact matches. The first
publication and every remote deletion need the operator's approval. This is not a CI
auto-publish workflow. Check the generated README's **Not synced** section for the current
build's omissions.
