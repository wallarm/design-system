# Public docs website (Rspress) replacing the published Storybook

> Status: proposed, 2026-10-22. Branch `docs/website`.
> Decisions marked **(user)** were made by the maintainer in conversation; **(call)** are the author's defaults and can be overridden.

## 1. Intent

`@wallarm-org/design-system` is open source, but its only public face is a Storybook on GitHub Pages. Storybook is a dev bench, not product documentation. We want a docs website on the level of shadcn/ui or Chakra UI, where an outside developer can, without asking the team:

- install the library, set up theming, wire it to their router;
- see what changed between versions and how to migrate;
- connect the MCP server to their AI agent, or point an agent at `llms.txt`;
- browse every component with live previews, copyable code, props and (for compound components) an interactive anatomy explorer.

Success: a first-time visitor finds Installation, Migrations, Changelog, MCP, llms.txt and Routing from the landing sidebar within five minutes, and every component page has working previews whose code can be pasted into an app.

## 2. Goals, non-goals, anti-goals

**Goals**
- Docs site built on an existing, actively maintained framework, not hand-rolled. **(user)**
- Examples come from Storybook stories, the same source the MCP already uses. No duplicated example code. **(user)**
- Built-in `llms.txt`, `llms-full.txt` and a `.md` twin of every page. **(user)**
- An "Explorer" section on compound components, modelled on Chakra UI's (`chakra-ui.com/docs/components/fieldset#explorer`). **(user)**

**Non-goals**
- Remote/hosted MCP endpoint. The site only documents how to run the npm package `@wallarm-org/mcp` locally. **(user)**
- Per-component Accessibility section, for now. **(user)**
- Versioned docs snapshots (v2 / v3 side by side). Latest only; majors ship weeks apart, migration guides + changelog cover history. **(call)**
- i18n. English only. **(call)**
- Fixing the empty `CHANGELOG.md` generator. Tracked as separate work; the site renders whatever semantic-release produces. **(call)**
- Retiring Storybook. It stays as the dev tool and E2E target. **(user)**

**Anti-goals** (failure even if it technically works)
- Example code on the site that differs from the stories, or can't be pasted into an app (relative imports, `(args) =>` wrappers, Storybook-only helpers).
- A second build toolchain or second React Compiler implementation in the monorepo.
- Breaking the Storybook-based E2E pipeline or its published URL used by tests.

## 3. Constraints (from the repo)

- Monorepo: pnpm 10.33.2 + Turborepo; `apps/*` is already a workspace glob. Node 24.
- Toolchain is Rspack: Rsbuild 2.2.x, Rslib, Rstest; shared `packages/configs/rsbuild-config` (`pluginReact({ reactCompiler: true })`, `CircularDependencyRspackPlugin`). TypeScript 7.0.2.
- DS styles are Tailwind v4 source, not prebuilt CSS. A host imports `tailwindcss`, `tw-animate-css`, `@wallarm-org/design-system/theme` and runs `@tailwindcss/postcss` (shared `@wallarm-org/tailwind-config/postcss`).
- Theme lives on `<html>`: `data-theme="dark"` and `data-frame-style`. `ThemeProvider.tsx:22-28` reads `localStorage` in `useState` initializers (breaks under SSR/prerender).
- No `'use client'` anywhere in DS `src/`.
- Global setup used by stories (`.storybook/preview.tsx`): `ThemeProvider`, `DateFormatProvider`, a singleton `<Toaster />`, `react-aria-polyfill.ts`; `.storybook/preview.css` adds `sb-annotation` classes.
- `dist/metadata/components.json` (schema `packages/mcp-core/src/schema.ts`) is generated by `scripts/metadata/generate.ts` on every DS build: description, importPath, props (name/type/required/description/default), variants, subComponents, examples (story source + JSDoc), tokens. The MCP reads it.
- `parse-examples.ts` only reads `{Name}.stories.tsx`; misses `stories/` subfolders (e.g. `FilterInput/stories/*`) and keeps `(args) =>` wrappers and relative imports.
- GitHub Pages: one site per repo, currently `https://wallarm.github.io/design-system/` serving Storybook with `assetPrefix '/design-system/'` (`.storybook/main.ts:31-34`). Deployed by `deploy-storybook` (`.github/workflows/main.yml:571-605`), main only.
- `SelectionBulkBar.e2e.ts:28-31,51-53` references the deployed Storybook at `wallarm.github.io/design-system`.

## 4. Decisions

### 4.1 Framework: Rspress v2 **(user)**
Chosen over Fumadocs for stack fit: same Rsbuild core (reuse `pluginReact({ reactCompiler: true })` via `builderConfig`), no RSC, no Next/TS7 friction, static `llms.txt`/`.md` output via `llms: true`, built-in local search, `base` option for the sub-path. Trade-off accepted: much smaller community than Fumadocs.

### 4.2 Location: `apps/docs` **(call)**
Private workspace app depending on `@wallarm-org/design-system: workspace:*`, resolving DS from `src` via the existing `development` export condition so stories and site share one module instance (one `ThemeProvider` context, one `Toaster`).

### 4.3 Hosting: one Pages artifact, two sites **(user)**
- Docs at `https://wallarm.github.io/design-system/` (Rspress `base: '/design-system/'`).
- Storybook at `https://wallarm.github.io/design-system/storybook/` (Storybook `assetPrefix` → `/design-system/storybook/`).
- `deploy-storybook` becomes `deploy-site`: assemble docs output + `storybook-static` into one directory, then the same `upload-pages-artifact` / `deploy-pages` steps.
- **Deploy only when a stable DS release happened (user).** Site and Storybook document what is on npm, never unreleased `main`. `deploy-site` runs after `release`, only if semantic-release published a new `@wallarm-org/design-system` version, and builds from that release commit/tag (so the freshly committed `CHANGELOG.md` entry is included). Pushes to `main` without a release deploy nothing. Builder decides how to detect "released" (semantic-release output / new `v*` tag) and whether docs+Storybook are rebuilt from the tag or the release commit's artifacts are reused.
- Update `SelectionBulkBar.e2e.ts` and any `STORYBOOK_URL` defaults to the new `/storybook/` path. E2E jobs that serve `storybook-static` locally keep working; only their serve path may need adjusting.
- Old Storybook deep links (`/design-system/?path=/docs/...`) redirect client-side to `/design-system/storybook/?path=...` (the docs root page or `404.html` checks for `?path=` / `iframe.html`). **(call)**

### 4.4 Rendering mode **(call, revised 2026-10-22)**
SSG (Rspress default) with SSG-MD (`llms: true`). Live story previews and the Explorer render client-only (`BrowserOnly`), so prerender never executes story code; in `.md` output a preview degrades to its code block. The only DS component that runs on the server is `ThemeProvider` (site root), which is made SSR-safe (guard `localStorage` access in its `useState` initializers). A pre-paint inline script sets `data-theme` from Rspress' stored appearance to avoid a flash.

### 4.5 Theme sync **(call)**
Rspress' dark mode toggles a class on `<html>`. The site's theme switch must also set `data-theme` (and keep `data-frame-style` default) so DS components and the site chrome agree. Map Rspress theme CSS variables to DS tokens so chrome and previews share colors and Geist fonts.

## 6. Component page

Section order (mirrors Chakra):
1. **Header** — name, one-line description (from `DESCRIPTION` / `components.json`), links: Source, Storybook (story URL). No Figma link while the file is private **(user)**.
2. **Preview / Code** — first story rendered live, toggle to its code.
3. **Usage** — import line (`@wallarm-org/design-system/<Comp>`) naming the component and its sub-components. No separate generated skeleton: the first example already shows the composition **(call)**.
4. **Examples** — every other story: JSDoc description, live preview, code.
5. **Props** — Markdown tables generated from `components.json` props (so they are searchable and land in `.md`/llms output); one table per detected sub-component.
6. **Explorer** — compound components only (those with `subComponents`).

**Pages are generated, not hand-written** **(call)**: a build step emits one MDX per component from `components.json` + the story module. Optional hand-written `apps/docs/docs/components/<name>.extra.mdx` (or similar) can be appended for extra prose (e.g. migrated public parts of `SimpleCharts/docs/*.md`, `Table/TABLE_DESIGN.md`, `Slider.llm.md`). Exact mechanism is the builder's.

### 6.1 Live previews from stories
- Render via Storybook portable stories (`composeStories` + `setProjectAnnotations` with a docs-specific subset of `preview.tsx`) so `meta.args`, story decorators and `fn()` args apply. Builder verifies portable stories work with `storybook-react-rsbuild` 3.6.0 / Storybook 10.6.1; if not, render the `StoryFn` directly with `meta.args`.
- Site root mounts once, client-side: `ThemeProvider`, `DateFormatProvider`, `<Toaster />`, the `react-aria-polyfill`.
- Copy `sb-annotation` styles into the site, or strip them from stories (see 6.3).

### 6.2 Shown code
Extend `scripts/metadata/parse-examples.ts` (so MCP benefits too):
- read every story file of a component, including `stories/` subfolders;
- strip the `(args) =>` wrapper and `{...args}` spreads;
- emit imports rewritten to public paths (`@wallarm-org/design-system/<Comp>`, `@wallarm-org/design-system/icons`);
- drop Storybook annotation labels — JSX elements whose `className` contains the `sb-annotation` / `sb-annotation-alt` class — from the shown code; the live preview still renders them **(user, 2026-10-22)**.
Keep `components.json` the single source for both MCP and site.

### 6.3 Story cleanup (incremental, non-blocking)
29 story files use local helper components and 36 use `sb-annotation`; their code isn't copy-pasteable. Not a launch blocker; tracked as follow-up, fixed component by component (existing rule: no wrappers in stories).

### 6.4 Explorer
Modelled on Chakra: a live preview of a representative story next to a list of parts. Hover a part → highlight it in the preview; click → pin selection.
- **Parts are discovered at runtime, not from metadata (call, revised 2026-10-22).** `components.json` `subComponents` misses whole compound components (Dialog, Tabs, Field, Toast… — `parse-props.ts` only sees sub-components whose `*Props` type is exported), and static "root slot" resolution needs AST unwrapping of aliases/Tooltip wrappers. So the parts list = the distinct `data-slot` values present in the rendered explorer preview, in DOM order — exactly what Chakra shows (slot names like `root`, `legend`, `content`).
- **No DS slot renames or additions for the Explorer (call):** slots don't always match sub-component names (e.g. `DialogHeader` renders `DrawerHeader` → `drawer-header`), and some parts have no slot; those simply don't appear. Renaming slots would break consumer CSS selectors and screenshots.
- Portaled parts (Ark `<Portal>` content, appended to `document.body`) are included: the explorer scans its preview container plus body-level nodes outside the site's app root, and rescans on DOM mutations (so opening a Dialog adds its parts).
- Shown for components whose story `meta` declares `subcomponents` (52 story files today).
- Which story feeds the explorer: default = the first story; overridable per component. **(call)**
- Hidden for components without sub-components.

## 7. AI outputs
- Rspress `llms: true` → `llms.txt`, `llms-full.txt`, per-page `.md`. Ensure previews degrade to the code block (not JSX noise) in `.md` output.
- "Copy page as Markdown" / "Open in Claude/ChatGPT" via Rspress' built-in LLM UI components.
- Publish `components.json` as a static file on the site (e.g. `/design-system/components.json`), versioned with the npm release that built it. **(call)**
- Register `@wallarm-org/mcp` in the MCP Registry (`server.json` + `mcpName`) — optional follow-up. **(call)**

## 8. CI changes
- `build` job: build docs after DS build (docs needs `components.json`); upload docs output as an artifact. Add docs outputs to `turbo.json` and docs paths to Biome `files.includes`.
- `deploy-storybook` is replaced by a separate `deploy-site.yml` workflow (`workflow_dispatch` with a `tag` input, `concurrency: pages` without cancel-in-progress). The `release` job dispatches it only when it created a stable `v*` tag on main; it rebuilds docs + Storybook from that tag. A separate workflow is needed because `main.yml` cancels in-progress runs on every push, which could otherwise drop a deploy for a release that already shipped. **(call, 2026-10-22)**
- Docs are built and smoke-checked in their own `docs` job on every push, parallel to E2E. **(call)**
- "Edit on GitHub" is hidden on generated pages (component pages, tokens, changelog); component pages link Source instead. **(call)**
- Storybook build switches `assetPrefix` to `/design-system/storybook/`.
- Keep pipeline under the 10-minute goal; docs build runs in parallel with E2E where possible.
- No PR previews (Pages can't); acceptable for now. **(call)**
